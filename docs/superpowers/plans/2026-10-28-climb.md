# The Climb Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace separate levels with an endless vertical climb of tall biomes joined by spring gates, with checkpoints, an altitude meter and an altitude-driven sky.

**Architecture:** A biome is one tall level (32 × 72 tiles). Physics, bodies and the solver read the level's own `rows` and `height`. The generator lays a zig-zag climbing path, splits it into four screen-sized segments with a checkpoint each, and proves the biome segment by segment with a start-state-aware solver. `climb.js` holds pure run logic (checkpoints, respawn, biome transfer, altitude); `game.js` drives it and `render.js` draws a camera-scrolled view.

**Tech Stack:** Vanilla JS modules, Canvas 2D, Web Worker, `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-28-climb-design.md`

## Global Constraints

- Zero dependencies, vanilla JS and Canvas.
- No code comments; names and structure carry intent.
- Every biome ships only if every segment is solved by chaining from the previous segment's end.
- A biome is `BIOME_SEGMENTS = 4` segments of `SEGMENT_ROWS = 18` rows; one tile is 2 m of altitude.
- `ceiling` and `wrap` mutators are excluded from the climb; `orbs` puzzle and `water` feature are excluded (no basin, no exit gating per segment).
- Run `npm test` before every commit; all tests must pass.

### Task 3: Run logic (`climb.js`)

**Files:**
- Create: `src/climb.js`
- Test: `test/climb.test.js`

**Interfaces:**
- Consumes: `initialState`, `playerSize` from physics; `overlaps` from level.
- Produces:
  - `standAt(level, state, checkpoint)` → state with player standing on the checkpoint (x centred, y on its base, zero velocity, grounded, `held` dropped, jumps refilled), world fields (bodies, flags, clock, crushed) kept.
  - `touchCheckpoints(level, state, touched)` → new `touched` array (ids added when the player overlaps a `checkpoint` object), each entry `{ id, y, snapshot }`.
  - `respawn(level, state, touched)` → state from the highest touched checkpoint whose `y >= state.y - TILE`, else `initialState(level)`.
  - `enterBiome(from, state, to)` → `initialState(to)` with player `x` kept, `y = to.height + state.y` (just below the floor), `vy = -launch` where `launch` clears the hatch under `to.rules`, `gravDir = to.rules.baseGravDir`.
  - `altitudeMetres(biomeIndex, level, state)` → `Math.floor(((biomeIndex * level.rows * TILE) + level.height - state.y) / TILE * 2)`.

### Task 4: Biome generation

**Files:**
- Modify: `src/generator.js` (replace level generation with `generateBiome`), `src/features.js` (local gap boxes, climb exclusions, gate spring power), `src/physics.js` (spring `o.vel ?? SPRING_VEL`), `src/worker.js`
- Test: `test/generator.test.js` (rewrite for biomes)

**Interfaces:**
- Produces: `generateBiome(seed, index)` → level with `rows = 72`, `index`, `title`, `hints`, `theme`, `palette`, `entryCol`, `exitCol`, objects including one `checkpoint` per segment boundary and a gate `spring` with `vel`, `exit` above the top opening, and `segments: [{ start, inputs }]` whose chained replays end on the next checkpoint and finally at the exit. `hatchCol(seed, index)` is the shared column of biome `index`'s floor hatch and biome `index - 1`'s top opening.

Generation steps inside `generateBiome`:
1. Puzzle pool by biome: biome 0 uses key, switch and portal puzzles; biome 1 adds `crateStep` and `plateDoor`; biome 2 adds `swing`; from biome 3 everything. Mutators by difficulty `min(1, index / 8)`; exclude tags `layout` for `ceiling`/`wrap`, keep `flood` at `rules.flood *= 0.6`.
2. Floor row `rows - 1` solid with the 2-wide hatch at `hatchCol(seed, index)` as `ONE_WAY`; spawn on the hatch. Ceiling row 0 solid except the opening at `hatchCol(seed, index + 1)`; top platform at row 3 under the opening with a gate spring whose `vel = sqrt(2 * gravity * 9 * TILE)`.
3. For each segment `k` (bottom first), with an rng sub-stream and up to 6 attempts: snapshot tiles, object count, `nextBit`, waypoints; lay tiers zig-zagging upward from the segment's entry node to its top node (tier rise `min(maxUp, 3)` rows, ladder steps between tiers as in spiral); pick a puzzle allowed in the climb and apply it to the segment's nodes; apply features; place a `checkpoint` on the segment's last node (`w: 24, h: 40`, standing on it); set `level.route` to the segment's route; bypass-check physics puzzles; solve from the chained start (`standAt` the previous checkpoint) to the checkpoint goal (or the exit for the last segment). On failure restore the snapshot and retry; after 6 failures, replace the segment with a plain ladder of steps and solve it.
4. Store `segments`, set `level.solution` to the concatenation.

- [ ] **Step 1: Write failing tests**: three seeds × first two biomes: `generateBiome` returns `rows === 72`, has 3 checkpoints, every `segments[k]` replays from its start to the next checkpoint (or exit) and `segments[k+1].start` equals `standAt` of the reached checkpoint; `hatchCol(seed, i + 1) === biome(i).exitCol`; generation is deterministic.
- [ ] **Step 2: Run** — FAIL.
- [ ] **Step 3: Implement** as above.
